<!-- #intro -->
Between pressing the power button and seeing a login prompt, a Linux machine runs a chain of programs. Each one prepares the system a little further and then hands control to the next. Knowing that chain matters for security because **whatever runs earlier controls everything that runs later**. Code that gets into the boot chain runs before the operating system, before any antivirus or EDR agent, and can hide from all of them.

| # | Stage | Main job | Hands over to |
| --- | --- | --- | --- |
| 1 | Firmware (UEFI or BIOS) | Test and initialise hardware, find a boot device | the bootloader |
| 2 | Bootloader (GRUB) | Load the kernel and initramfs into memory | the kernel |
| 3 | Kernel + initramfs | Start the kernel, find and mount the real root filesystem | `/sbin/init` |
| 4 | init (systemd, PID 1) | Start and supervise everything in user space | services |
| 5 | Services | Logging, networking, SSH, cron, web server… | login |
| 6 | Login | Authenticate a user and start their shell | you |

<!-- #firmware -->
[[Firmware]] is software stored on a chip on the motherboard. It is the first code the CPU runs. It performs the [[POST]] (power-on self-test), initialises the CPU, memory and devices, and then looks for something to boot according to its configured boot order.

There are two kinds:

- **Legacy [[BIOS]]**, the original PC firmware, reads the first 512-byte sector of the boot disk (the *master boot record*, MBR) and jumps into the tiny program stored there.
- **[[UEFI]]**, its modern replacement, understands partitions and filesystems. It reads a small FAT32 partition called the [[EFI System Partition|esp]] (ESP) and runs a boot program stored on it as a normal file. On a running Linux system the ESP is usually mounted at `/boot/efi`.

UEFI also brings [[Secure Boot]]: the firmware holds a set of trusted public keys and refuses to run a boot program whose digital signature does not match one of them. Each later stage then checks the next, forming a *chain of trust*.

<!-- #bootloader -->
A [[bootloader]] is a small program whose only job is to load the operating system kernel. Almost every Linux distribution uses [[GRUB]] 2 (GRand Unified Bootloader).

On a Secure Boot machine the firmware cannot run GRUB directly, because GRUB is signed by the distribution, not by Microsoft, whose key is the one built into most PCs. So the firmware first runs **shim**, a tiny loader signed by Microsoft that contains the distribution’s own key; shim then verifies and starts GRUB.

GRUB reads its configuration from `/boot/grub/grub.cfg` (generated by `update-grub`; on RHEL-family systems the path is `/boot/grub2/grub.cfg`), shows a menu, and loads two files from `/boot` into memory:

- the compressed kernel, `vmlinuz-<version>`
- the matching [[initramfs]], `initrd.img-<version>` (Debian/Ubuntu) or `initramfs-<version>.img` (RHEL/Fedora)

It also passes the [[kernel command line]], a string of options such as `root=UUID=… ro quiet splash`, that tells the kernel where the root filesystem is and how to behave. You can read the command line of the running kernel in `/proc/cmdline`.

<!-- #kernel -->
The kernel decompresses itself, detects hardware, sets up memory management and the scheduler, and starts its built-in drivers.

It then faces a chicken-and-egg problem: the real root filesystem may need drivers or tools to reach it (a RAID array, LVM, an encrypted disk that needs a passphrase), but those drivers live *on* the root filesystem. The [[initramfs]] solves this. It is a small compressed archive that the bootloader loaded into RAM next to the kernel. The kernel unpacks it as a temporary root filesystem and runs the programs inside it. They load the needed drivers, ask for the disk encryption passphrase if there is one ([[LUKS]] is the standard Linux disk encryption), mount the real root filesystem, and switch over to it.

Finally the kernel starts the first user-space program, `/sbin/init`.

<!-- #systemd -->
The first user-space process is called [[init]] and always gets **process ID 1**. On almost every current distribution, `/sbin/init` is a link to [[systemd]]. You can confirm with `ps -p 1` or `ls -l /sbin/init`.

[[PID 1|pid-1]] is special:

- Every other user-space process is its child, grandchild or later descendant.
- Orphaned processes (whose parent died) are adopted by PID 1.
- If PID 1 ever exits, the kernel panics. The kernel also protects it: PID 1 ignores any signal it has not explicitly chosen to handle, even `SIGKILL` from root.

systemd starts the rest of the system according to [[unit]] files, small configuration files that describe services, mount points, timers and more. Units are grouped into [[targets|target]], named states the system can be in. Servers normally boot to `multi-user.target` (everything running, text logins); desktops boot to `graphical.target`. You will work with units and `systemctl` in the processes lesson.

<!-- #services -->
To reach its target, systemd starts [[daemons|daemon]], long-running background services, in parallel wherever their dependencies allow: the journal and syslog for logging, networking, `cron` for scheduled jobs, `sshd` for remote logins, and whatever the server is for, such as a web server or database. Each runs under the user account its unit file specifies.

<!-- #login -->
Finally someone needs to log in. On a physical console, a program called [[getty]] prints the `login:` prompt; desktops show a graphical login screen instead; and remote users connect through `sshd`.

In every case the credentials are checked by [[PAM]] (Pluggable Authentication Modules), a library of small modules that each perform one check: compare the password hash in `/etc/shadow`, check that the account is not expired, ask for a one-time code, and so on. If PAM says yes, a session is created, a shell starts under your user ID, and your startup scripts (`/etc/profile`, `~/.profile`, `~/.bashrc`) run.

<!-- #security -->
**Boot-level compromises are rare but severe.** A [[bootkit]] (malware in the bootloader) or a firmware implant runs before the operating system and survives reinstalling it. For a SOC analyst, the more common boot-related findings are simpler: someone with physical access to a laptop or server, or an attacker abusing a virtual machine console.

**Physical access usually means game over unless disks are encrypted.** Without full-disk encryption, anyone who can boot the machine from a USB stick, or edit the kernel command line at the GRUB menu, can read and modify every file. Full-disk encryption with LUKS (plus a firmware password and GRUB password) is the defence. This is why company laptops require disk encryption.

**Secure Boot, TPM and measured boot raise the bar.** Secure Boot blocks unsigned bootloaders and kernels; with kernel *lockdown*, unsigned kernel modules are refused too. A [[TPM]] (Trusted Platform Module) can record a hash of every stage so that tampering is detectable, and can release disk encryption keys only if the boot chain is unchanged.

**Most attackers persist at the systemd stage, not in firmware.** Creating a systemd service or timer, adding an `@reboot` cron job or modifying shell startup files all give an attacker [[persistence]]: their code runs again after every reboot or login. These map to MITRE ATT&CK techniques T1543.002 (Systemd Service), T1053.003 (Cron) and T1546.004 (Unix shell configuration modification). Reviewing enabled units and recently changed files in `/etc/systemd/system` is standard incident-response practice.
