<!-- #one-tree -->
Windows gives every disk a letter (`C:`, `D:`). Linux has **one single tree** of directories, starting at the [[root directory]], written `/`. Every disk, partition, USB stick and network share appears somewhere *inside* that tree.

A few ground rules:

- **Paths** use forward slashes. An [[absolute path]] starts at the root, like `/home/analyst/notes.txt`. A [[relative path]] starts from your current directory, like `notes.txt` or `../alice`.
- `.` means “this directory”, `..` means “the parent directory”, and `~` is a shell shortcut for your [[home directory]] (`/home/analyst` for the user analyst).
- Names are **case-sensitive**: `Report.txt` and `report.txt` are different files.
- Files whose names start with a dot, like `.bashrc`, are [[hidden|dotfile]]: `ls` skips them unless you add `-a`. This is a convention, not a security feature, and attackers like it too (a directory called `/tmp/.x` is easy to overlook).
- Extensions such as `.txt` or `.sh` mean nothing to the kernel. Whether a file can be run depends on its permissions and contents, not its name.

<!-- #fhs -->
Where things live is standardised by the [[Filesystem Hierarchy Standard|fhs]] (FHS), so every distribution looks broadly the same. These are the directories you will use constantly:

| Path | Contains | Why a defender cares |
| --- | --- | --- |
| `/etc` | System-wide configuration (text files) | Accounts, sudo rules, SSH and cron config live here |
| `/var/log` | Log files | Your evidence. `auth.log` / `secure`, `syslog` / `messages`, the journal |
| `/home` | Users’ home directories | Shell history, SSH keys, personal startup files |
| `/root` | Home directory of the root user | Root’s history and keys. Not the same as `/` |
| `/tmp` | Temporary files, writable by everyone | Favourite staging area for attackers |
| `/bin`, `/usr/bin` | Programs for all users | Should only contain packaged, unmodified binaries |
| `/sbin`, `/usr/sbin` | Programs for administration | Same |
| `/boot` | Kernel, initramfs, GRUB config | Tampering here affects the boot chain |
| `/dev` | Device files | Raw disks must not be readable by normal users |
| `/proc`, `/sys` | Virtual files generated by the kernel | Live view of processes and kernel settings |
| `/usr` | Installed software and libraries | `/usr/local` holds software installed by hand |
| `/opt` | Self-contained third-party software | Often installed with sloppy permissions |
| `/run` | Runtime data since boot (in RAM) | PID files, who is logged in |
| `/mnt`, `/media` | Mount points for extra filesystems | Removable media |

On most current distributions `/bin`, `/sbin` and `/lib` are just [[symbolic links|symlink]] to their counterparts under `/usr`, a layout called *merged /usr*. Explore the tree below: select any directory or file to see what it is for and why it matters.

<!-- #mounts -->
Because there is only one tree, extra storage is attached by [[mounting|mount]] it onto an existing directory, which then becomes a [[mount point]]. After `sudo mount /dev/sdb1 /mnt`, the contents of that partition appear under `/mnt`. The root filesystem itself is mounted at `/` during boot, and `/etc/fstab` lists what else to mount automatically.

```
$ findmnt -t ext4,vfat,tmpfs
TARGET     SOURCE     FSTYPE OPTIONS
/          /dev/sda2  ext4   rw,relatime
/boot/efi  /dev/sda1  vfat   rw,relatime,fmask=0077,dmask=0077
/tmp       tmpfs      tmpfs  rw,nosuid,nodev
```

Mount options are a security tool. The three to know:

- `noexec`: programs on this filesystem cannot be executed directly
- `nosuid`: SUID and SGID bits (lesson 4) are ignored here
- `nodev`: device files here are not treated as devices

Hardening guides recommend mounting `/tmp`, `/var/tmp` and `/dev/shm` with all three. Not every filesystem is on a disk: [[tmpfs]] lives entirely in RAM and disappears at reboot.

Useful commands: `df -h` (free space per filesystem), `findmnt` or `mount` (what is mounted where and with which options), `lsblk` (disks and partitions).

<!-- #everything-file -->
A famous Unix design principle is “[[everything is a file]]”. Not literally everything, but a surprising amount of the system is reached through the same open/read/write interface as ordinary files:

- **[[Device files|device-file]]** in `/dev` represent hardware and kernel features. Writing to `/dev/null` throws data away, reading `/dev/urandom` gives random bytes, `/dev/sda` is a whole disk.
- **Virtual files** in `/proc` and `/sys` are generated by the kernel when you read them. `cat /proc/1/cmdline` asks the kernel about PID 1; nothing is stored on disk.
- **Pipes and sockets** used for communication between processes also appear as files.

The first character of each `ls -l` line tells you the file type:

| Char | Type | Example |
| --- | --- | --- |
| `-` | regular file | `/etc/passwd` |
| `d` | directory | `/home` |
| `l` | symbolic link | `/bin -> usr/bin` |
| `c` | character device (stream of bytes) | `/dev/null`, `/dev/tty` |
| `b` | block device (disk-like) | `/dev/sda` |
| `s` | socket | `/run/systemd/notify` |
| `p` | named pipe (FIFO) | created with `mkfifo` |

<!-- #inodes -->
What *is* a file on disk? Two separate things:

1. An [[inode]] (index node): a record holding the file’s **metadata** and the location of its data. It stores the file type, permission bits, owner (UID) and group (GID), size, timestamps, a [[link count]], and pointers to the data blocks. Each inode has a number, unique within its filesystem.
2. A **directory entry**: a name, stored in a directory, that points to an inode number.

The inode does **not** contain the file’s name. A directory is simply a list of *name → inode number* pairs. `ls -i` shows inode numbers and `stat` shows everything in the inode:

```
$ stat /etc/passwd
  File: /etc/passwd
  Size: 1878       Blocks: 8          IO Block: 4096   regular file
Device: 8,2        Inode: 524542      Links: 1
Access: (0644/-rw-r--r--)  Uid: (    0/    root)   Gid: (    0/    root)
Access: 2026-10-26 09:02:11.311204880 +0000
Modify: 2026-10-20 14:02:37.000000000 +0000
Change: 2026-10-20 14:02:37.112090551 +0000
```

The three timestamps are worth memorising for investigations:

- **Access** (*atime*): last read. Often only updated lazily (`relatime`), so treat with care.
- **Modify** (*mtime*): last change to the contents. This is what `ls -l` shows.
- **Change** (*ctime*): last change to the inode itself (contents, permissions, owner, link count). Users cannot set ctime directly, which makes it useful when an attacker has faked the mtime.

<!-- #links -->
Because names and inodes are separate, one inode can have several names. That gives us two kinds of links:

| | [[Hard link]] | [[Symbolic (soft) link|symlink]] |
| --- | --- | --- |
| Created with | `ln target name` | `ln -s target name` |
| What it is | Another name for the **same inode** | A small separate file that stores a **path** |
| `ls -l` shows | A normal file; link count goes up | `l` type and `name -> target` |
| If the original name is deleted | Still works: data stays until the last name is gone | Breaks (“dangling link”) |
| Across filesystems | No (inode numbers are per filesystem) | Yes |
| To directories | No (not allowed for users) | Yes |

`rm` does not really “delete a file”: it removes one name (the syscall is literally `unlink`). The kernel frees the inode and data only when the link count reaches zero **and** no process still has the file open.

<!-- #security -->
**Permissions on a handful of files protect the whole system.** `/etc/shadow` holds password hashes; if it becomes readable, attackers can crack them offline. `/etc/passwd`, `/etc/sudoers` and anything in `/etc/cron.d` or `/etc/systemd/system` must only be writable by root. File locations you saw in this lesson are exactly the checklist for the hardening lesson.

**World-writable places are attacker workspaces.** `/tmp`, `/var/tmp` and `/dev/shm` are writable by every account, including a compromised web server running as `www-data`. Malware is often downloaded there, sometimes into hidden directories like `/tmp/.x`. Mounting them `noexec,nosuid,nodev` blocks simple “download and run” attacks. When you investigate a host, `ls -la /tmp /var/tmp /dev/shm` is one of the first things to run.

**Deleted is not gone.** Because data lives until the last name *and* the last open file descriptor disappear, malware sometimes deletes its own binary after starting. The process keeps running, and `ls -l /proc/<PID>/exe` shows the path with `(deleted)` at the end, a strong indicator of compromise. Investigators can even copy the binary back out of `/proc/<PID>/exe`.

**Links can be weapons.** If a privileged program writes to a predictable path in `/tmp`, an attacker can plant a symlink there pointing to, say, `/etc/passwd`, and trick the program into overwriting it. Modern kernels block the classic form of this attack with `fs.protected_symlinks` and `fs.protected_hardlinks`, which you can check with `sysctl fs.protected_symlinks`.

**Timestamps tell a story.** When building a timeline of an incident, mtime and ctime help you see which files changed and when. Attackers can fake mtime (`touch -d`), but the ctime then shows when they did it.
